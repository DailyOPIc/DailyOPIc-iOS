## 2. 주 사용자와 사용 맥락 [방향]

- OPIc 등급이 필요한 한국인 학습자. 특히 **대학생 · 취업준비생 · 직장인**.
  (앱의 설문 옵션도 학생/직장인/구직으로 되어 있다 — `Models/BackgroundProfile.swift` [VERIFIED])
- 학원·스터디가 아니라 **혼자 모바일로 짧게 반복 연습**하는 상황이 핵심.
  하루 10~20분, 부담 없이 반복하는 경험이 중요하다.
- 주요 목표 등급은 **IM2~IH 중심**이되 특정 등급에 앱을 한정하지 않는다.
  AL 목표 사용자도 자연스럽게 쓸 수 있어야 한다.
  (서버 등급 체계는 NL~AL 전체를 다루고, 예상 등급에는 IL 하한 클램프가 있다. [VERIFIED])
- **시험 직전 모의고사 앱이 아니라, 평소 매일 말하기를 지속하는 학습 서비스**다.

## 3. 포지셔닝 / 대체 불가능한 지점 [방향]

핵심 포지셔닝:

> **매일 실제로 말하고, AI 피드백을 받아 OPIc 실력을 개선하는 모바일 스피킹 학습 앱**

우선순위 순서(이 순서가 화면 설계의 우선순위이기도 하다):

1. 앱을 열면 **바로 문제를 받고 실제로 말하게** 만드는 낮은 진입장벽
2. 사용자의 **실제 음성 답변을 STT로 처리**하고 AI가 분석
3. **예상 등급 / 잘한 점 / 개선점 / 참고 답안**으로 즉시 피드백
4. OPIc 시험 맥락에 맞는 문제와 모의고사 경험
5. 이를 **매일 반복**할 수 있는 모바일 학습 루틴

주의:
- 실제 OPIc 시험 흐름 반영은 중요하지만, **구현된 범위 이상으로 "실제 시험을 완벽히 재현한다"고
  포지셔닝하지 않는다.** 구현된 시험 구조는 §5에 VERIFIED로만 적었다.
- 가격/가성비는 **보조적 장점**이다. 가장 중요한 차별점은
  **실제 발화 → AI 분석 → 다시 말하기의 반복 학습 경험**이다.

## 5. OPIc 시험 맥락 구현 범위 [VERIFIED]

여기 적힌 것만 사실이다. 이 밖의 시험 재현(예: 실제 OPIc의 Self Assessment 재현,
시험 안내 음성, 시험 시간 총량 등)은 **구현되어 있지 않다.**

### 배경 설문(Survey)
- `BackgroundSurvey`: `status`(학생/직장인/구직/해당없음), `residence`(혼자/가족/룸메이트/기숙사/기타),
  `leisure`/`hobbies`/`sports`/`travel` 다중 선택. **최소 3개 토픽 선택 필수**(서버·클라 양쪽 검증).
  (`Models/BackgroundProfile.swift`, `app/models/api.py`)
- 설문 입력 UI는 **모의고사 플로우 안의 `.survey` 단계**에 있다(`MockExamViewModel.Phase.survey`).
  온보딩에는 설문 단계가 없다.
- 데일리 문제 생성은 저장된 설문을 재사용하고, 없으면 `BackgroundSurvey.defaultSurvey`
  (학생/가족/영화·음악·카페)로 요청한다. (`PracticeViewModel.performLoad()`)
- 서버는 설문 토픽을 문제 생성 프롬프트에 넣어 개인화한다.

### 자가 진단 난이도
- 실제 OPIc의 Self Assessment를 그대로 재현한 것이 아니라 **1~6단계 자가 선택**이며,
  각 단계에 예상 등급 범위 텍스트가 붙는다. (`SelfAssessmentLevel`, `OnboardingView`)
- 난이도 변경은 **하루 1회**. 무료는 리워드 광고 시청, 유료 플랜은 서버 auto-verify로 광고 없이 변경.
  한도 초과 시 "난이도 변경은 하루 한 번만 가능해요" 안내 + 홈으로 돌아가기.
  (`OnboardingView.submitSelection`, `plans.reward_max_for(TARGET_LEVEL_CHANGE) == 1`)
- ⚠️ **카피 불일치(리뉴얼 시 수정 대상)**: `SetupView`와 `OnboardingView.guidanceText`는 플랜과 무관하게
  "변경하려면 광고를 끝까지 봐야 해요"라고 고정 표기한다. 확인 다이얼로그(`TargetLevelConfirmationDialog`)는
  유료 플랜을 정확히 구분("무료로 바꾸기")한다. 유료 사용자에게 잘못된 안내가 노출되는 상태다.

### 모의고사 (15문항)
- 서버 `validate_mock_blueprint`가 강제하는 구조:
  - Q1 = introduction
  - Q2~Q10 = survey 기반, **3문항씩 3개 콤보**(Q2-4 / Q5-7 / Q8-10), 각 콤보는 같은 topicId·comboId
  - Q11~Q12 = roleplay
  - Q13 = unexpected, Q14 = comparison, Q15 = advanced
- **시험 중 난이도 조정 1회**: 앞부분(front) 답변 후(`requiresAdjustmentAfter`, 기본 7문항)
  easier / same / harder 선택 → 뒷부분(tail) 문제를 그 난이도로 생성.
  (`MockExamViewModel` phase `.adjustment`, 서버 `adjust_mock_session`)
- 문항당 타이머 **180초**(`remainingSeconds = 180`).
- 세션 단계: `awaiting_start_ad → generating_front → answering_front → awaiting_adjustment_ad →
  generating_tail → answering_tail → awaiting_result_ad → evaluating → completed`.
  무료 플랜은 start/adjustment/result 3개 광고 게이트, 유료는 auto-verify로 광고 없이 통과.
- 진행 중 세션 복원 가능(`currentMockSession`, "이어서 하기").

### 데일리 연습
- 데일리 문제 세트는 **Q2~Q15의 14문항 풀**이며 **introduction(자기소개) 문항을 포함하지 않는다**
  (`validate_daily_pool`). 진행바에 표시되는 번호는 인덱스가 아니라 **실제 문항 번호 Q2~Q15**다.
- **토큰 = 하루에 받을 수 있는 "새 문제 세트" 수.** 세트 생성(초기 로드 + 리프레시)에서 1토큰 소모,
  **세트 안에서의 평가(분석)는 무제한**(`reserve_request`, 쿼터 미차감).
  (`routes.py` `reserve_practice` vs `reserve_request`)
- 리프레시는 광고가 아니라 토큰 소모이며, 다이얼로그에서 easier/same/harder를 고를 수 있다
  (`DailyRefreshDialog`).
- 문항 간 앞뒤 이동 가능하며, 이미 분석한 문항은 저장된 결과를 다시 볼 수 있다(`analyzedResults`).

## 6. 발화 → 분석 파이프라인 [VERIFIED]

- **STT는 온디바이스 Apple Speech**(`SFSpeechRecognizer(locale: en-US)`), 부분 인식 결과 스트리밍,
  구두점 자동 삽입(`addsPunctuation`), `.record` 카테고리 + `.default` 모드.
  마이크·음성인식 권한 필요. (`Services/Speech/SpeechRecognitionService.swift`)
- 녹음 원본 오디오는 파일로 저장되어 평가 요청에 함께 업로드되고, 서버가 **ffprobe/ffmpeg로
  발화 길이·무음 비율·WPM(`AudioMetrics`)** 을 계산한다. (`app/services/audio.py`)
- 문제 프롬프트 읽어주기는 **AVSpeechSynthesizer(en-US) TTS**. (`Services/Audio/PromptPlaybackService.swift`)
- 데일리 평가 결과(`PracticeEvaluation`): `predictedLevel`, `confidence`, 5개 점수
  (taskFulfillment / grammar / vocabulary / discourse / fluency), `strengths`, `improvements`,
  `correctedAnswer`, `targetGap`, `sampleAnswer`, `rubrics`, `audioMetrics`, `disclaimer`.
- 모의고사 결과(`MockEvaluation`): 위 항목 + `overallFeedback` + **문항별 피드백/모범답안(perQuestion, 1~15)**.
- 예상 등급에는 **IL 하한 클램프**가 있다(`_clamp_min_level`).

## 7. 구독 · 사용량 정책 (production behavior — 임의 변경 금지) [VERIFIED]

서버 `app/services/plans.py`가 **단일 진실 소스**이고, 클라이언트는 `/v1/capabilities`의
`plan` + `quotaPolicy`로 UI를 게이팅한다. 최종 판정은 항상 서버다.

### 7.1 데일리 토큰 (제품 정의)

**데일리 토큰 1개 = 새로운 Daily 문제 세트 1개.**

- 토큰은 **세트를 받을 때** 1개 소모된다. 하루 첫 세트 생성과 리프레시(새 문제 받기 ·
  난이도 조정)가 모두 여기에 해당한다. (`routes.py` `create_practice_set` /
  `refresh_practice_set` → `reserve_practice`)
- 한 번 시작한 세트 안에서는 **답변 기록 · 채점(평가) · 결과 열람에 토큰이 들지 않는다.**
  세트 내 평가 횟수는 제한이 없다.
- **모의고사는 데일리 토큰과 별개**다. 플랜별 모의고사 횟수로만 제한된다.
- UI 문구는 항상 "데일리 토큰"이다. `quota` · `credit` · `practice_credit` ·
  `reward intent` · `reserve_practice` 같은 구현 용어는 사용자에게 노출하지 않는다.
  반대로 백엔드 식별자를 마케팅 용어로 개명하지도 않는다.

### 7.2 플랜별 실제 강제 한도

| 모의고사 광고 게이트 | 있음(3회) | 없음 | 없음 | 없음 |
| 광고 노출 | 있음 | 없음 | 없음 | 없음 |
| 분석 depth | `summary` | `full` | `full` | `full` |
| 취약점 복습 세트 (`review_set`) | ✗ | ✗ | ✗ | 서버만 허용 (앱 진입점 없음) |

- 가격은 **`package.storeProduct.localizedPriceString`(RevenueCat)에서만** 온다.
  클라이언트에 원화 상수를 두지 않는다(`PlanEntitlement.monthlyPriceKRW`는 삭제됨).
- 시험 대비 패스는 `exam_pass` 엔타이틀먼트 → **pro 동급**으로 매핑된다(신규 발급 없음).
- **결과 화면 잠금은 무료↔유료 한 곳뿐**이다(`ResultUnlock.showsCoaching = plan.isPaid`).
  교정 답안 · 모범 답안 · 목표 갭이 유료 전용이고, 유료 플랜끼리는 분석 내용이 같다.
  서버도 depth가 `summary`면 이 셋을 **생성하지 않는다**(AI 비용 절감).

### 7.3 강제되지 않는 항목 — 페이월에서 광고하지 않는다

| 항목 | 상태 | 페이월 노출 |
|---|---|---|
| 학습 기록 보관 기간 (7일/30일/전체) | `historyDays`가 capabilities에 있으나 **서버에 기록 조회 API 자체가 없다**. 기록은 기기 로컬 SwiftData이며 `trimPracticeHistory`가 전 플랜 동일하게 최근 50건만 남긴다 | **제거됨** |
| 취약점 복습 세트 | 서버 `/v1/question-sets/review`는 프로 전용으로 강제되지만, **앱이 이 엔드포인트를 호출하는 화면이 없다** | **제거됨** |
| 리프레시 리워드 상한 (`refresh_ad_bonus`) | 리프레시는 이제 데일리 토큰을 소모하고 광고 리워드를 쓰지 않는다. 별도 혜택이 아니다 | 노출 안 함 |

이 세 항목은 backlog다. 앱에서 실제로 도달 가능해지는 시점에 페이월 문구로 되살린다.
`DailyOPIcTests/PaywallTests.swift`의 `copyNeverPromisesUnenforcedBenefits`가 회귀를 막는다.
- **스마트 기능(예상 등급 추이 · 취약 유형 분석 · 주간 리포트)은 전 플랜 무료 공개**다.
  `StudyInsightsSection`의 세 카드 모두 `locked: false`이고, 페이월에도 그렇게 명시되어 있다.
  **리뉴얼에서 이걸 다시 잠그지 않는다.**
- 결제: RevenueCat SPM 패키지가 **현재 프로젝트에 실제로 연결되어 있다**
  (`XCRemoteSwiftPackageReference "purchases-ios"` + `RevenueCat in Frameworks`).
  RevenueCat App User ID = Firebase uid.
- 웹훅: EXPIRATION·REFUND만 즉시 free 강등. CANCELLATION·BILLING_ISSUE는 `expiresAt`까지 유지.
- 플랜 변경 즉시 반영: 포그라운드 복귀(`scenePhase == .active`) 및 `plan` 변경 시 usage/capabilities 재조회.
- 통계 탭의 기간 필터(최근 7일 / 30일 / 전체)는 **로컬 기록 기준이며 플랜으로 잠기지 않는다.**

## 9. 접근성 — 기본 품질 기준 [방향]

접근성은 별도 기능이 아니라 **SwiftUI 구현의 기본 요구사항**이다. 최소 기준:

- VoiceOver: 의미 있는 accessibility label/value/hint, 장식용 요소는 숨김
- Dynamic Type: 큰 글자에서 잘리거나 겹치지 않을 것 (`fixedSize(horizontal:vertical:)` 적극 사용)
- 충분한 contrast (라이트/다크 모두)
- Reduce Motion 고려 — 애니메이션/로딩 인디케이터 대체 경로
- 충분한 touch target (최소 44×44pt)
- Light Mode / Dark Mode 모두 지원

현재 상태 [VERIFIED]:
- 색상은 이미 라이트/다크 동적 대응(`Resources/Colors/AppPalette.swift`가 dynamic UIColor provider 사용).
- `accessibilityReduceMotion`은 4개 파일에서만 사용(`OPIcGuideView`, `AILoadingOverlay`,
  `RecordingButton`, `AppLoadingIndicator`).
- accessibility label/value/hint 계열 호출은 앱 전체 **16건 / 7개 파일**뿐이다.
  → **접근성은 현재 부분 적용 상태이며, 리뉴얼의 실질적인 개선 대상이다.**

## 10. 리뉴얼에서 지켜야 할 원칙 [방향]

하지 말 것:
- 현재 구현되지 않은 기능을 디자인을 위해 만들어내기(특히 §8 항목).
- 한국어 UI를 억지로 다국어 구조로 전환하기.

## 16. 학습 캘린더 (Calendar Foundation) [구현됨 · G2]

DailyOPIc는 답변 채점 앱이 아니라 **목표 등급/시험일까지 매일 무엇을 할지 관리하는
AI OPIc 학습 플래너**다. G2는 그 플래너의 토대다.

### 16.1 범위

- 캘린더 탭 신설(기존 탭 재설계 없음), 미설정 시 온보딩 / 설정 후 대시보드.
- 학습 계획 설정의 서버 영속화, 오늘 할 일 · 주간 · 월간 표시, 자동 완료 집계, 스트릭.
- **자동 재계획(G3), 플랜별 잠금(G4), 알림(G5), AI 플래너(G8)는 포함하지 않는다.**

### 16.2 온보딩 5단계

| 단계 | 질문 | 저장 위치 |
|---|---|---|
| 1 | 목표 등급이 어떻게 되세요? | **기존 목표 등급 그대로**(§16.4) |
| 2 | 시험일이 정해졌나요? (선택 · 과거 불가) | `studyPlan.examDate` |
| 3 | 언제 공부할 수 있나요? (최소 1일) | `studyPlan.studyWeekdays` |
| 4 | 하루에 얼마나 공부하고 싶나요? | `studyPlan.intensity` |
| 5 | 언제 공부할까요? (로컬 시각) | `studyPlan.preferredStudyTime` |

5단계에서 **알림 권한을 요청하지 않고 알림을 예약하지도 않는다.** 시각만 저장하며
화면에 "알림 기능은 학습 계획 설정 이후 사용할 수 있어요."라고 적는다(G5가 이 값을 쓴다).

### 16.3 저장 위치 (단일 진실)

- 서버: `GET/PUT /v1/users/me/study-plan` → Firestore `userProfiles/{uid}.studyPlan`.
  기존 사용자 문서에 `studyPlan`이 없으면 **오류가 아니라 `configured=false`**다.
  파괴적 마이그레이션 없음, 컬렉션 전수 스캔 없음.
- 로컬: `AppPreferences.studyPlanSettings`는 **서버 값의 사본**일 뿐이다. 네트워크가
  끊겼을 때 캘린더가 빈 화면이 되지 않게만 쓴다.
- 저장하지 않는 것: 전사(transcript) · 녹음 · AI 응답 본문 · 파생값(예상 완료일 등) ·
  구독 플랜(엔타이틀먼트에서 실시간으로 온다).

### 16.4 목표 등급은 복제하지 않는다

목표 등급의 진실은 이미 `AppPreferences.targetLevel` + 서버 `userProfiles.targetLevel`
(`PUT /v1/users/me/target-level`)이다. 캘린더는 이 값을 **읽기만** 하고, 변경은 기존
난이도 재선택 화면(`OnboardingView`, 하루 1회 · 광고/유료 자동 검증 규칙 포함)으로 보낸다.
`StudyPlanRequest`에 `targetLevel` 필드는 없다(`StudyCalendarTests`가 이를 강제).

### 16.5 예측 휴리스틱 (검증된 학습 곡선이 아니다)

상수는 전부 `StudyPlanEstimatorConfig` 한 곳에 있다.

| 상수 | 값 | 의미 |
|---|---|---|
| `baseTotalSets` | 20 | 목표에 이미 도달했을 때도 권장하는 유지 학습량(세트) |
| `setsPerLevelStep` | 12 | 목표까지 등급 한 단계당 추가 세트 |
| `assumedLevelStepsWhenUnknown` | 2 | 최근 등급을 모를 때 가정하는 단계 차 |
| `recentLevelMaxAgeDays` | 60 | 이보다 오래된 분석 결과는 현재 실력으로 보지 않음 |
| `minimumTotalSets` / `maximumTotalSets` | 12 / 120 | 권장 총량 클램프 |
| `maximumForecastDays` | 365 | 완료일 탐색 상한(넘으면 날짜 없음) |

계산: `권장 총 세트 = clamp(20 + 12 × max(0, 목표.rank − 현재.rank))` →
`하루 목표 = min(강도 세트, 플랜 Daily 토큰 한도)`.
G3부터 일정은 이 총량이 아니라 **남은 학습량**으로 만든다(§17.1).
OpenAI를 호출하지 않으며 등급 예측 모델도 아니다.

> **예측의 의미: "권장 학습 계획을 끝내는 데 걸리는 예상 기간"이지, 해당 날짜에
> OPIc 등급을 취득한다는 뜻이 아니다.** 화면에도 "실제 OPIc 등급 달성을 보장하지
> 않아요"를 항상 함께 노출한다.

### 16.6 하루 학습량과 플랜

- 강도 → 희망 세트: 가볍게 1 · 꾸준히 2 · 집중 3.
- **실효 목표 = min(희망 세트, 현재 플랜의 하루 Daily 토큰 한도)**
  (무료 1 · 베이직 3 · 플러스 10 · 프로 20 — 진실은 서버 `quotaPolicy.practiceDaily`).
- **프로의 20토큰은 한도지 숙제가 아니다.** 한도가 희망 세트를 늘리는 일은 없다.
- 무료 + 집중처럼 한도에 걸리면 "오늘 권장 1세트 · 현재 무료 플랜 최대 1토큰"이라고
  설명만 한다. **여기서 페이월을 열지 않는다(G4).**

### 16.7 하루 상태

| 상태 | 표기 | 규칙 |
|---|---|---|
| 휴식 | `moon.zzz` | 선택하지 않은 요일 |
| 예정 | `circle.dotted` | 학습일 · 오늘 이후(또는 오늘) · 완료 0 |
| 일부 완료 | `circle.lefthalf.filled` | 1세트 이상 · 목표 미만 |
| 완료 | `checkmark.circle.fill` | 목표 이상 |
| 놓침 | `exclamationmark.circle` | 지난 학습일 · 완료 0 |

색만으로 구분하지 않고 항상 기호 + 문구를 함께 쓴다. 각 날짜의 목표는 **그날 배정된
학습량**으로 판정하며, 지난 날은 그날 값으로 고정된다(§17.4).

### 16.8 완료 정의와 중복 방지

- **세트를 받는 것(토큰 소모)은 완료가 아니다.** 그 세트에서 **AI 분석이 처음
  성공했을 때** 완료 1세트로 센다(`PracticeViewModel.evaluatePendingRecording()`의
  성공 경로).
- 저장은 `StudySetCompletionRecord(setId, completedAt)`, `setId`가 **유일 키**다.
  재분석 · 결과 재진입 · 화면 재등장 · 네트워크 재시도가 중복으로 세지 않는다.
- 토큰 소모 · 평가 로직 · Daily 세트 획득 동작은 **변경하지 않았다.**
- `PracticeHistoryRecord`(문항 단위 · 최근 50개만 보관)로는 세트 단위 일별 완료를
  복원할 수 없어 별도 원장을 뒀다. 서버 `dailyUsage`는 토큰 예약을 세므로 "세트를
  열기만 한 날"까지 완료로 잡히기 때문에 쓰지 않는다.

### 16.9 스트릭

연속으로 **완료**한 학습일 수. 계획된 휴식일은 끊지 않고, 목표에 못 미친 지난
학습일은 끊는다. 아직 끝나지 않은 오늘은 끊지 않으며 미래 날짜는 세지 않는다.
스트릭 프리즈 · 복구 아이템 · 공유 · 업적은 만들지 않는다.

### 16.10 시험일

로컬 달력 기준 "시험 D-n". 시험일이 있으면 남은 학습량을 시험 전 학습일에 다시
나눈다(§17.3). 제공하는 행동은 학습 설정 수정 · 시험일 수정뿐이며, **업셀 ·
학습량 자동 증가 · 날짜 자동 변경 · 페이월 트리거는 없다.** 시험일과 권장 계획
완료일은 서로 다른 값으로 표시한다.

### 16.11 설정 수정

시험일 · 공부 요일 · 강도 · 학습 시간을 한 화면에서 고친다(목표 등급은 §16.4 경로).
저장하면 앞으로의 일정만 다시 계산되고 **이미 쌓인 완료 기록과 지난 날의 배정량은
그대로 남는다**(§17.4, §17.6).

## 17. 적응형 학습 플래너 [구현됨 · G3]

G2는 "권장 학습량 ÷ 하루 목표"를 매일 처음부터 다시 계산했다. 하루를 놓치든 두 배로
하든 화면의 예상 완료일이 같았다. G3는 계획을 **실제 학습 기록에 반응**하게 만든다.
여전히 결정론적이며 OpenAI를 호출하지 않는다(같은 입력 → 항상 같은 일정).

### 17.1 남은 학습량이 계획의 기준이다

```
남은 학습량 = max(0, 권장 총 학습량 − 인정 완료 학습량)
```

- **인정 완료**: 계획 시작일(`studyPlan.createdAt`의 로컬 날짜, 오늘보다 늦지 않게 클램프)
  **이후**의 고유 성공 세트 완료. 계획을 세우기 전의 연습이 새 계획을 미리 끝낸 것으로
  둔갑하지 않는다. 같은 세트를 여러 번 분석해도 1회다(§16.8).
- 계획 대비 더 한 학습도 전부 남은 학습량을 줄인다 → 예상 완료일이 앞당겨진다.
  보너스 재화 · 업적 · 게이미피케이션은 주지 않는다.
- 놓친 학습은 사라지지 않고 **전체 남은 학습량으로 돌아간다** → 완료일이 뒤로 밀린다.
- 음수가 되지 않으며, 0이 되면 계획은 완료 상태다(§17.5).

### 17.2 평소 모드 — 놓친 몫을 다음 날에 몰아주지 않는다

시험일이 없거나 평소 속도로도 시험 전에 끝나면 **평소 모드**다. 하루 목표는 강도에서
나온 기본 학습량 그대로다.

> 남은 10세트 · 하루 2세트 · 월~금에서 월요일을 통째로 놓쳐도 **화요일은 여전히 2세트**다.
> 4세트가 되지 않는다. 대신 완료 예정일이 하루(또는 다음 학습일까지) 밀린다.

이건 편의가 아니라 제품 규칙이다. 하루 놓쳤다고 다음 날 두 배를 요구하는 플래너는
그 지점에서 버려진다.

### 17.3 시험일이 있을 때 — 압축 모드

1. 먼저 평소 모드로 계산한다. 완료일이 **시험 전날 이하**면 그대로 평소 모드다.
2. 넘어가면 **시험 전날까지의 선택 요일**에 남은 학습량을 균등 분배한다(압축 모드).
   시험 당일에는 의무 학습을 배정하지 않는다.
3. 하루 상한(§17.7)까지 채워도 모자라면 **부족 상태**를 그대로 드러낸다(§17.8).

**균등 분배 알고리즘** (`AdaptiveStudyPlanner.balanced`):

```
학습일 n일, 남은 학습량 s
기본 = s / n (정수 나눗셈), 나머지 = s % n
앞에서부터 나머지 개의 날짜에 +1세트
```

예: 11세트를 5일에 → `3, 2, 2, 2, 2` (`11, 0, 0, 0, 0`이 아니다).
휴식일은 압축 모드에서도 휴식일이다. 계획이 촉박하다는 이유로 선택하지 않은
토·일을 몰래 쓰지 않는다.

### 17.4 지난 기록은 다시 계산하지 않는다

**과거 = 바뀌지 않는 학습 이력. 오늘/미래 = 적응형.**

날짜별 배정 학습량은 로컬 하루 단위로 `StudyDayPlanRecord`(로컬 전용, `localDate`가
유일 키)에 고정한다. 지난 날짜는 이 기록만 읽고, 오늘·미래는 현재 적응형 계획에서
읽는다. 완료 기록(진실 A)과 배정량 기록(진실 B)은 끝까지 분리되어 있고, 배정량 기록에
완료 수를 복제하지 않는다.

그래서 강도를 "꾸준히 → 집중"으로 바꿔도 **어제의 `완료 1 / 1`이 `일부 완료 1 / 3`으로
바뀌지 않는다.** 공부 요일을 바꿔도 지난 날의 학습일/휴식일 진실이 뒤집히지 않는다.
휴식일(배정 0)은 아예 기록하지 않으며, 보관 기간은 1년이다.

**캘린더를 매일 열지 않아도 마찬가지다.** 월요일에 캘린더를 보고 화·수·목은 열지
않은 채 금요일에 들어와도, 화·수·목이 휴식으로 바뀌지 않는다. 기록이 없는 지난
학습일은 그날 적용되던 계획으로 되살려 보여주고(완료 0 → 놓침, 일부 → 일부 완료,
배정량 이상 → 완료), 그 값을 그대로 고정한다. 이미 고정된 기록이 있으면 언제나
기록이 이긴다. 설정을 바꿀 때는 **바뀌기 전 설정으로 오늘까지를 먼저 고정**하므로,
열지 않은 날들이 나중에 새 설정으로 되살아나지 않는다.

### 17.5 계획 완료

남은 학습량이 0이면 모드는 `완료`이고 **더 이상 의무 학습을 만들지 않는다.**
"권장 학습 계획을 완료했어요."라고만 말한다. 자율 연습은 평소대로 가능하다.

### 17.6 설정을 바꿨을 때

| 바꾼 값 | 결과 |
|---|---|
| 학습 시각 | 학습량·일정 변화 없음 |
| 강도 | **앞으로만** 반영. 지난 날 배정량·상태 그대로 |
| 공부 요일 | **앞으로만** 반영. 지난 날 상태 그대로 |
| 시험일 | 모드가 바뀔 수 있음(평소 ↔ 압축 ↔ 부족). 이력은 그대로 |
| 목표 등급(§16.4) | 권장 총량 재계산 → 완료량 유지 → 남은 학습량 재계산(음수 없음) |

설정 수정은 **진행 상황을 초기화하지 않고 계획 시작일도 다시 잡지 않는다.**
완료 기록을 삭제하지 않는다.

### 17.7 하루 상한 — 촉박해도 넘지 않는 선

```
기본 학습량 = min(강도 세트, 플랜 Daily 토큰 한도)      (가볍게 1 · 꾸준히 2 · 집중 3)
하루 상한   = min(플랜 Daily 토큰 한도, 기본 학습량 + 2, 5)
```

| 플랜 | 강도 | 토큰 한도 | 기본 | 상한 |
|---|---|---|---|---|
| 무료 | 가볍게 | 1 | 1 | 1 |
| 베이직 | 꾸준히 | 3 | 2 | 3 |
| 플러스 | 꾸준히 | 10 | 2 | **4** |
| 프로 | 집중 | 20 | 3 | **5** |

플러스의 10토큰, 프로의 20토큰은 **한도지 숙제가 아니다.** 어떤 플랜에서도 하루
의무 학습량이 5세트를 넘지 않는다(`productMaximumAdaptiveDailySets`).

### 17.8 시간이 부족할 때 — 거짓말하지 않는다

상한까지 채워도 시험 전에 못 끝내면 조용히 상한을 넘기지 않고 상태를 드러낸다.

- "현재 설정으로는 시험 전 권장 학습량을 모두 완료하기 어려워요."
- "남은 권장 학습 18세트 · 현재 일정에서 시험 전 최대 12세트 가능"
- 예상 완료일은 시험일이 아니라 **실제로 끝나는 날짜**다. 못 끝내는데 시험일을
  완료일로 적지 않는다.
- 제공하는 행동은 **학습 설정 수정 · 시험일 수정**뿐이다. 페이월을 열거나 상위 플랜을
  권하거나 계획을 자동으로 바꾸지 않는다(G4에서 다룬다).

### 17.9 타임존

로컬 하루의 경계는 기기 설정이 아니라 **계획에 저장된 `timezoneIdentifier`**가 정한다.
계획 시작일 · 오늘 · 시험 D-day · 배정량 기록 키 · 일정 생성이 모두 이 달력을 쓴다.
기기 타임존이 바뀌어도(여행) 지난 기록의 날짜 키는 그대로이고, 계획은 여전히 저장된
타임존 기준으로 계산된다. 여행 동기화 기능은 만들지 않았다.

### 17.10 문구

- "남은 학습량을 앞으로의 일정에 다시 나눴어요."
- "오늘 계획보다 2세트 더 학습했어요. 남은 일정에 반영했어요."
- "시험일까지 남은 기간을 반영해 학습량을 조정했어요."
- "현재 설정으로는 시험 전 권장 학습량을 모두 완료하기 어려워요."

실패 · 뒤처짐 · 게으름 같은 수치심 문구는 쓰지 않는다.

## 18. 캘린더 플랜 게이팅 [구현됨 · G4]

캘린더는 **전 플랜이 쓴다.** 유료가 사는 것은 접근권이 아니라 **자동화의 깊이**다.
무료 사용자의 계산을 일부러 틀리게 만들지 않는다 — 무료 캘린더도 수학적으로 참이다.

### 18.1 플랜별 실제 동작

| | 무료 | 베이직 | 플러스 | 프로 |
|---|---|---|---|---|
| 캘린더 · 오늘 진행 · 완료 상태 · 스트릭 · 완료 예상일 | ✅ | ✅ | ✅ | ✅ |
| 자동 일정 재조정 (`calendarAutoReplan`) | ✗ | ✅ | ✅ | ✅ |
| 최근 평가를 반영한 학습 계획 (`calendarEvaluationAdaptive`) | ✗ | ✗ | ✅ | ✅ |
| 시험일까지 역산한 일정 (`calendarExamBackplan`) | ✗ | ✗ | ✅ | ✅ |

프로는 **플러스와 캘린더 기능이 같다.** G4에서 프로 전용 일정 기능을 새로 만들지 않았다.

### 18.2 각 권한이 실제로 바꾸는 계산

| 권한 | 켜짐 | 꺼짐 |
|---|---|---|
| 자동 재조정 | 남은 학습량을 남은 학습일에 재분배(`balanced`) | 하루 배정량 고정(`fixedQuota`) · 남은 세트/스트릭/날짜 상태는 그대로 참이고 일정 길이만 줄어든다 |
| 평가 반영 | 최근 평가 등급으로 권장 총량 산출 | `recentLevel = nil` 고정 → 목표 등급 기준의 결정적 기본값 |
| 시험일 역산 | 시험일까지 압축(`compressed`) · 불가하면 `insufficientTime` | 압축하지 않는다. **D-day와 "시험 전에 다 못 끝낸다" 경고는 그대로 보여준다**(`finishesAfterExam`) |

무료에서 잠긴 자동화를 **프리미엄 문구로 가장하지 않는다.** 자동 재조정이 꺼져 있으면
"남은 일정에 반영했어요"라고 말하지 않고 "오늘 계획보다 N세트 더 학습했어요"까지만 쓴다.

### 18.3 권한의 진실은 서버다

`GET /v1/capabilities`의 `quotaPolicy`에 4개 필드가 추가됐다(추가만 · 하위 호환).

```json
"quotaPolicy": {
  "calendarEnabled": true,
  "calendarAutoReplan": false,
  "calendarEvaluationAdaptive": false,
  "calendarExamBackplan": false
}
```

- `calendarEnabled`는 **항상 true**다. 클라이언트는 이 값으로 화면을 잠그지 않으므로
  디코딩하지도 않는다(읽지 않는 값을 모델에 넣지 않는다).
- `calendarWeaknessPlanner`는 **존재하지 않는다.** 취약점 기반 일정은 구현이 없다(§15.1).

### 18.4 클라이언트 폴백은 한 곳에만 있다

`CalendarFeaturePolicy.resolve(capabilities:plan:)`.

- 서버 스냅샷의 플랜이 **현재 플랜과 같을 때만** 서버 값을 쓴다.
- 그 외(오래된 서버 · 필드 없음 · capabilities 없음 · 방금 업그레이드해서 스냅샷이 낡음)는
  전부 `fallback(for: plan)` 표 하나로 간다. 방금 업그레이드한 사용자가 낡은 스냅샷 때문에
  잠기지 않는다.
- 화면과 플래너는 플랜을 직접 보지 않는다. `canAutoReplan` / `canUseRecentEvaluation` /
  `canBackplanToExam` 셋만 본다. `AdaptiveStudyPlanner` 안에 플랜 분기를 흩뿌리지 않았다.

### 18.5 잠긴 기능 UX

- 월간 보기를 어지럽히지 않는다. 주간 요약과 달력 사이의 **"학습 플랜 기능" 카드 한 곳**에만
  모아 둔다. 잠긴 게 없으면 카드 자체가 사라진다.
- **캘린더에 들어왔다는 이유로 페이월을 열지 않는다.** 로드 · 완료 예상 부족 · 학습 누락 ·
  시험일 임박 어느 것도 자동으로 페이월을 열지 않는다. 잠긴 행을 **직접 눌렀을 때만** 연다
  (`PaywallSource.calendarLocked`).
- 계측은 `AppTelemetry.calendarFeatureLockedTap`. 파라미터는 고정 enum
  `feature`(`auto_replan` · `evaluation_adaptive` · `exam_backplan`)와 `current_plan`뿐이다.
  전사·답변·UID·자유 텍스트는 남기지 않는다.
- VoiceOver는 "자동 일정 재조정, 잠김, 베이직부터 이용 가능"처럼 한 문장으로 읽는다.

### 18.6 플랜이 바뀌어도 과거는 다시 쓰이지 않는다

배정량 고정(`StudyDayPlanRecord`)은 `baseDailyTarget`만 쓰고 자동화 권한을 보지 않는다.
따라서 업그레이드·다운그레이드는 **미래 계획만** 바꾼다. 과거 배정량 · 완료 기록 · 스트릭 ·
학습 설정은 그대로다. 다운그레이드가 캘린더를 초기화하거나 설정을 지우지 않는다.

### 18.7 페이월 카피

G1에서 걸어 둔 "캘린더"·"일정" 전면 금지는 **해제**하고, 대신 각 플랜이 **실제 구현된
캘린더 기능만** 광고하는지 검사한다(`PaywallTests.calendarCopyMatchesEachPlanCapabilities`).
비교표에 "학습 일정 자동화" 행이 추가됐다: 기본 캘린더 / 자동 재조정 / 평가 반영 · 시험일 역산 /
평가 반영 · 시험일 역산. 프로에 없는 캘린더 기능을 붙이지 않는다.

## 19. 학습 알림 [구현됨 · G5]

목표는 하나다 — **"오늘 공부하기로 한 날이면, 정한 시간에 한 번 알려준다."**
리텐션 기능이지 결제 유도나 불안 조성 장치가 아니다. **전 플랜이 똑같이 쓴다**(유료 잠금 아님).

### 19.1 로컬 알림만 쓴다 — 서버 없음

`UNUserNotificationCenter`의 로컬 알림(`UNCalendarNotificationTrigger`)만 쓴다.
일정은 이미 기기에 다 있고, 알림 내용에 서버만 아는 정보가 없다. 따라서 **FCM · 푸시 토큰 ·
`aps-environment` 엔타이틀먼트 · 서버 잡 · Cloud Scheduler를 추가하지 않았다.** 백엔드 변경 0줄.

### 19.2 권한은 사용자가 켤 때만 요청한다

앱 실행 · 캘린더 진입 · 학습 설정 저장 · 구매 직후 · 오류 뒤 — **어디서도 자동으로 시스템
권한 창을 띄우지 않는다.** 캘린더의 "학습 알림" 칸에서 `학습 알림 켜기`를 누르면 먼저 앱 안
설명("공부할 시간에 알려드릴까요?")을 보여주고, 거기서 `알림 켜기`를 눌러야 시스템 창이 뜬다.
`나중에`는 아무것도 바꾸지 않는다.

| 시스템 권한 | 화면 |
|---|---|
| 미결정 | 켜기 CTA. 누르기 전에는 요청하지 않는다 |
| 허용 · 임시(provisional) | "매일 21:00 · 학습일에만" + `시간 변경` · `알림 끄기` |
| 거부 | "알림이 꺼져 있어요." + `설정에서 알림 허용`. 권한 창을 다시 띄우지 않는다 |

### 19.3 앱 설정과 시스템 권한은 별개다

`AppPreferences.studyRemindersEnabled`는 "이 기기에서 받고 싶다"는 **사용자 의도**이고,
실제 발송 권한은 언제나 OS다. 두 값이 조용히 어긋나지 않도록 화면이 항상 실제 상태를 말한다.
거부 상태에서 iOS 설정으로 권한을 켜고 돌아오면 **앱에서 다시 켜지 않아도** 예약이 살아난다.
이 값은 기기별 설정이라 **서버로 보내지 않는다.** StudyPlan API 스키마는 그대로다.

### 19.4 무엇을 언제 알리나

알림 일정은 캘린더와 **같은 일정**(`AdaptiveStudyPlan.upcomingDays`)에서 나온다.
알림 전용 플래너가 따로 없다 — 자동 재조정 · 평가 반영 · 시험일 역산이 그대로 반영된다.

- 시각은 학습 설정의 **공부 시간(`preferredStudyTime`)** 하나뿐이다. 별도 알림 시각 필드를 두지 않는다.
- 하루 **최대 1개**. 휴식일 · 배정량 0인 날 · 권장 학습을 다 끝낸 뒤에는 알리지 않는다.
- 시험 **당일**에는 학습 숙제 알림을 보내지 않는다.
- 오늘 배정량을 알림 시각 전에 다 끝내면 오늘 알림은 사라진다.
- 앞으로 **30일**치만 예약한다(rolling horizon). 백그라운드 작업·크론 없이 앱이 열릴 때 갱신한다.

### 19.5 문구

제목은 언제나 "오늘의 Daily 학습".

| 상황 | 본문 |
|---|---|
| 아직 시작 전 | "오늘 Daily 연습 2세트가 예정되어 있어요." |
| 일부 완료 | "오늘 계획까지 1세트 남았어요." |
| 시험 7일 이내 | 앞에 "시험까지 3일 · "만 덧붙인다 |

스트릭 위협 · 죄책감 · "뒤처지고 있어요" · 합격 확률 · 등급 보장 문구는 쓰지 않는다.

### 19.6 타임존

날짜·시각은 기기 타임존이 아니라 **학습 계획 타임존(`timezoneIdentifier`)**으로 정한다.
예약 트리거에 그 타임존을 그대로 넣어 여행 중에도 "그 지역의 21시"가 흔들리지 않는다.

### 19.7 재조정

식별자는 `dailyopic.study-reminder.<yyyy-MM-dd>`로 로컬 날짜에서 결정된다. 같은 입력으로
몇 번 돌려도 대기 알림이 같다(중복 없음). 정리는 **이 접두사의 알림만** 건드린다 —
`removeAllPendingNotificationRequests()`를 쓰지 않는다.

재조정 시점: 알림 켜기 · 앱 활성화 · 캘린더 화면 갱신 · 학습 설정 저장 성공 · Daily 세트 완료 ·
엔타이틀먼트 갱신. **알림만을 위한 새 API 호출은 하지 않는다.** 재조정 실패가 학습 성공이나
설정 저장 성공을 되돌리지 않는다.

플랜이 바뀌면 **미래 알림만** 다시 맞춘다. 과거 기록·배정량은 그대로이고, 알림으로
업그레이드를 권하지 않는다.

### 19.8 프라이버시 · 계측

알림 문구는 고정 템플릿뿐이다. 전사·답변·오디오·UID·스토어 정보·AI 피드백·자유 텍스트를
넣지 않는다. 계측은 기존 `AppTelemetry`(OSLog)에 **사용자 결정 세 개**만 남긴다 —
`study_reminder_enable_tapped` · `study_reminder_permission_result`(authorized·denied·provisional) ·
`study_reminder_disabled`. 예약된 알림 하나하나·날짜·문구는 남기지 않으며, 로컬 예약만으로는
전달·열람을 알 수 없으므로 전달률 지표로 쓰지 않는다.

## 20. App Store 평점 요청 [구현됨 · G6]

### 20.1 원칙 — 네이티브 요청만

Apple의 **네이티브 평점 요청**(SwiftUI `RequestReviewAction`) 하나만 쓴다.
자체 별 UI · "앱이 마음에 드시나요?" 만족도 확인 · NPS 설문 · 평점 요청 보상 ·
강제 리뷰 흐름 · 좋은 평가만 스토어로 보내는 분기는 **없다**.

창을 띄울지는 **Apple이 정한다.** 앱은 창이 떴는지·평가가 등록됐는지 알 수 없고,
알 수 없는 것을 안다고 기록하지도 않는다. 창이 뜨지 않아도 결과 화면은 평소와 똑같다.

### 20.2 언제 묻는가 — 성공한 학습 결과에서만

**연습 분석이 성공해 결과가 화면에 뜬 순간** 한 곳에서만 요청한다.

묻지 않는 곳: 앱 시작 · 캘린더 · 알림 탭 · 녹음 완료 · 세트 수령 · 토큰 소모 ·
결과가 뜨기 전의 API 응답 · 연속 학습일 · 계획 완료 · 페이월 · 구매 · 복원 · 광고 시청 ·
오류 화면. 요청 지점이 한 곳뿐이라 이 목록은 저절로 지켜진다.

### 20.3 "긍정적인 순간"은 높은 점수가 아니다

여기서 긍정적인 순간은 **결과 경험이 성공적으로 전달된 것**이지 좋은 등급이 아니다.
예상 등급 · 목표 달성 여부 · 향상도 · 답변 품질 점수는 자격 조건에 **들어가지 않는다.**
NL 결과를 받은 사용자와 IH 결과를 받은 사용자는 완전히 똑같이 취급된다.
높은 평가만 골라 받는 것은 평점 조작이다.

### 20.4 자격 조건

| 조건 | 값 |
|---|---|
| 성공한 분석 | 3회 이상 |
| 서로 다른 학습일 | 2일 이상 |
| 요청 쿨다운 | 30일 |
| 배포 경로 | TestFlight는 언제나 제외 |

근거는 캘린더가 쓰는 완료 원장(`StudySetCompletionRecord`) 그대로다. 세트당 한 줄이고
분석이 성공했을 때만 쓰이므로 실패한 분석·재분석·결과 재진입·화면 재렌더링은 두 번 세지 않는다.
"서로 다른 날"은 기기 현재 달력 기준의 날짜로 센다(앱 설치 후 48시간이나 실행 횟수가 아니다).

### 20.5 30일 쿨다운

마지막으로 **요청을 시도한** 시각을 기기에 남긴다(`lastReviewRequestAttemptAt`).
창이 실제로 떴는지는 알 수 없으므로 시도를 기준으로 삼는다. 30일이 되기 전에는 다시 묻지
않고, 30일이 지나면 다른 조건이 모두 맞을 때 다시 자격이 생긴다. 같은 결과 화면이 여러 번
그려져도 요청은 한 번뿐이다.

### 20.6 기존 사용자

남아 있는 기록으로 조건이 증명되면 그대로 쓴다. 기록이 부족하면 **추측하지 않는다.**
과하게 묻느니 덜 묻는다. 기존 사용자는 새 학습이 쌓이면 자연스럽게 자격을 얻는다.
자격을 만들기 위한 데이터 이관·삭제는 하지 않는다.

### 20.7 상태 · 계측

리뷰 상태는 **이 기기에만** 있다. 서버로 보내지 않고, Firestore 상태·자격 API·서버 카운터·
스케줄 잡을 만들지 않는다(백엔드 변경 없음).

계측은 기존 `AppTelemetry`(OSLog)에 두 개뿐이다 — `app_review_eligible` ·
`app_review_request_attempted`(둘 다 `context=successful_practice_result`).
표시·제출·성공을 주장하는 이벤트는 만들지 않는다. 등급·평점·리뷰 텍스트·전사·답변·UID는
어떤 형태로도 남기지 않는다.
